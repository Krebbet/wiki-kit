# Locating an Object from its Last Known Position — object records built for re-finding, the search escalation, and what verification is possible on a geometry-only sensor

**Summary.** A `locate_object(name)` that starts from a last-known location needs three things the object-side wiki does not yet supply: a record that stores **where the robot was standing when it last saw the thing** (not just where the thing was), a **search escalation** for when it is not there, and a **verification test** the rig's sensor can actually run. The classical object schemas — SLAM++/Fusion++/Quadric/Cube landmarks, Hydra/ConceptGraphs scene-graph nodes, ROS `vision_msgs/Detection3D` — store pose + extent + class + a confidence and **none of them stores the observing viewpoint or a usable last-seen time**; the systems that *do* store it are the 2025–26 memory agents built specifically to go back and look (STAR, EmbodiedLGR, "Where Did I Leave My Glasses?"), which is the precedent for adding that field here rather than an invention of this page.
The single most load-bearing empirical result is SLiM's (ICRA 2020): a **known but noisy static prior on object location made search *worse* than having no prior at all** (cup found 33 % of trials vs 83–100 %), and modelling that prior's uncertainty recovered the gap. A last-known location is exactly such a prior, so `locate_object` must treat it as a *hint with a decaying covariance*, never as a place the object is.
On a single 1.1 m LiDAR plane "identified" can honestly mean only **re-observed at the expected place with a compatible 2-D footprint** — a persistent handle, not a name; the published 2-D-range recognisers (DROW, DR-SPAAM) are single-class detectors trained on hundreds of thousands of scans, which is not a route this rig has. Tilt sweeps buy height and therefore *category-scale* discrimination; the camera is what buys identity.

## 0. What the existing pages already settle — do not re-derive these

The June object campaign settled most of the *representation* question, and this page builds on it rather than repeating it:

- [[world-model-architecture]] settles the **layered form factor** (slow structural anchor / fast object layer / change-detection process / ephemeral live layer), the **Layer-2 record** (`instance_id`, metric `map_pose` + covariance, multi-view embeddings, metric dims, category, `last_seen_ts`, `state ∈ {present, moved, removed, uncertain}`, `version`, append-only `history`), the **revisit loop** (relocalise → re-detect → data-associate → classify add/moved/removed → version), the rule that **confidence decays rather than the record being deleted**, the **N-consecutive-miss guard** before committing `removed`, and the point that `τ_move` must sit above the pose-error floor. It also rejects dense volumetric/per-point-semantic form factors for this project. Its one weakness for the present purpose: it predates the rover and assumes hloc + stereo depth throughout.
- [[object-fingerprint-memory]] settles the **identity matcher**: DINOv2 ViT-S/14 over CLIP for instance-level re-ID, multi-view storage with max-over-views cosine, a precision-favouring threshold (provisionally 0.75), best-vs-second-best margin as a confidence signal, and the honest status that this is validated on synthetic colour-distinct objects only.
- [[semantic-object-memory]] and [[scene-graph-world-model]] settle the **scene-graph design space** (Hydra, ConceptGraphs, HOV-SG, Tag Map, DovSG — including DovSG's 94–95 % scene-change-detection accuracy); [[dynamic-object-handling]] settles the **three timescales** and their mechanisms (STVL, DynaSLAM, POCD's 80.2 % precision / 3.0 % FPR, iRobot's reject-and-revert down to 1.41 % failure).
- [[point-cloud-object-segmentation-models]] settles how to get **object proposals** out of our data (BEV connected components, not a learned 3-D model); [[3d-shape-completion-for-object-footprints]] settles **footprint completion** (retrieval + deformation); [[room-segmentation-floor-plan]] settles rooms and doors; [[tidybot-deep-dive]] and [[home-tidying-robots]] settle what the tidying systems do.

**What none of them answers** — and what this page is for: how an object record must be shaped so a robot can *go back and look*, what to do when it is not there, and what verification means when the rover's only sensor is a 2-D LiDAR plane.

## 1. What shipping and research systems actually store per object

| System | Pose | Extent | Identity | Appearance | Time | Confidence | Mobility prior |
|---|---|---|---|---|---|---|---|
| **SLAM++** (CVPR 2013) | 6-DoF in pose graph | from a **pre-scanned CAD model** | class = which database model | none (geometry matching) | none | detection score | none |
| **Fusion++** (3DV 2018) | 6-DoF; the pose graph is the *only* persistent map | per-object TSDF at object-dependent resolution + 3-D foreground mask | per-object instance | none | none | **existence probability** (for spurious detections) | none |
| **QuadricSLAM** (RA-L 2019) | dual quadric = position + orientation + **size in one 9-DoF primitive** | ellipsoid | class from the detector | none | none | in the factor covariance | none |
| **CubeSLAM** (T-RO 2019) | cuboid (position, yaw, dimensions) | oriented box | class | none | none | proposal score | **yes — a motion model for dynamic objects** |
| **Hydra / Clio** (IJRR 2024 / RA-L 2024) | node centroid in the graph | bounding primitive | open-set (Clio) | CLIP-class embedding | graph is rebuilt/optimised, not time-indexed per node | — | Clio's granularity is **task**-determined (Information Bottleneck) |
| **ConceptGraphs** (ICRA 2024) | centroid + point cloud | point cloud + box | instance node | **CLIP feature + caption** | detection count | detection count | none |
| **POCD** (RSS 2022) | object pose | TSDF model | instance | semantic class | updated per traversal | **stationarity score (Beta) + change magnitude (Gaussian)** | **yes — that is the stationarity score** |
| **Khronos** (RSS 2024) | object pose | mesh/TSDF | instance | semantic | **explicitly 4-D: fast short-term window + slow long-term factor graph** | — | implicit in the two-process split |
| **ROS `vision_msgs/Detection3D`** | `PoseWithCovariance` | `BoundingBox3D` (centre + size, 6-DoF) | `string id` "for consistency across messages", *may be empty* | **none** | header stamp only | per-hypothesis `score` | none |

Three things fall out. The first two are established; the third is this page's judgement.

**(a) The classical schemas store where the *object* was, never where the *robot* was.** None of SLAM++, QuadricSLAM, CubeSLAM, Hydra or ConceptGraphs records the pose the observation was made from. `vision_msgs` is the cleanest case: `ObjectHypothesisWithPose.pose` is the *object's* and is explicitly unstamped, the only time is the source frame's `header.stamp`, and the ROS ecosystem has **no standard persistent-object-memory message at all** — `moveit_msgs/CollisionObject` comes closest (stable `id`, subframes, incremental `ADD/MOVE`) but is a collision world, not a perception memory. Fusion++ is the near-miss: it keeps **BRISK snapshots binned at 15° of view-angle difference**, i.e. the viewpoint, but for relocalisation rather than for revisiting.

**(b) The systems built for re-finding *do* store it — and that is the precedent to copy.** STAR's long-term memory record is literally `(t, xₜ, embed(oₜ), oₜ)` — timestamp, **robot pose at observation time**, embedding, and the raw image, with a spatial index over the robot poses so the agent can ask what was visible from a place; it keeps the raw observation precisely so it can be revisited. EmbodiedLGR stores per node an embedded label plus **last-associated pose and last-observed time**. So `last_seen_from: {pose, tilt, range, incidence}` is not an invention — it is the field the 2025–26 memory-agent line converged on, and it converts "go to the object's coordinates" into "reproduce the observation that worked".

**(c) The permanence prior is what separates a map from a memory.** Among the classical schemas only POCD (stationarity score) and CubeSLAM (dynamic-object motion model) carry anything like it; the dedicated line makes it central — Rosen/Mason/Leonard's **persistence filter** (ICRA 2016) is the canonical form, storing last-observation time plus three sufficient statistics for exact constant-time Bayesian updates under a survival-time prior, and Perpetua (IROS 2025) extends it with *emergence* filters for things that come back. EDA226 already computes the rig's version — permanent / semi-permanent / unverified by cross-map agreement with per-map visibility — so the rig is, unusually, ahead of most schemas on exactly the field that says how much to trust a stale position.

Worth noting for calibration: **no shipping consumer system maintains object identity across sessions autonomously.** iRobot's persisted artefact is a user-confirmed **rectangle** (Image Review promotes an obstacle to a Keep-Out Zone — no class, no pose, no instance); Meta Quest persists per-anchor UUIDs across sessions but offloads the labelling to a human in Space Setup; Amazon Astro's durable object memory is user-taught doors and windows with an open/closed state. Where cross-session identity exists commercially, it is achieved by **relocalising the frame**, not by re-identifying the object — which is an argument for this rig's locked-substrate approach, since a correct frame reduces association to a within-frame nearest-neighbour test.

## 2. Where the object layer lives relative to a frozen map

Established practice is unambiguous: **a separate layer keyed to the metric map, never inside it.**

- Fusion++ makes the object pose graph the only persistent representation and keeps per-object volumes detachable, so one object's geometry can be re-integrated without touching the others; Panoptic Multi-TSDFs (ICRA 2022) generalises this to **submaps** at object granularity, so a changed object is a changed submap and the rest of the reconstruction is untouched.
- Khronos factorises the problem in *time*: a fast process for short-term dynamics inside an active window, a slow factor graph for long-term change. The frozen map is the slow process's output.
- iRobot's production lesson ([[dynamic-object-handling]]) is the same claim from the shipping side: the semantic layer is kept separate from and derived over the geometric map, with reject-and-revert when an update is inconsistent.
- Nav2's costmap-filter architecture is the same pattern in the navigation stack: a static map plus *filters and layers keyed to it*, never a rewritten static map ([[stop-and-go-navigation-on-a-locked-map]]). Worth knowing before anyone proposes putting objects in the costmap: **every Nav2 layer writes a single `unsigned char` cost per cell and carries no identity whatsoever**, the costmap filters are raster PGM/PNG masks, and the spatio-temporal voxel layer stores exactly one double per voxel — the marking wall-clock time. Nav2's only persistent identified geometry is the Vector Object Server (`CircleObject`/`PolygonObject`: stable UUID + geometry + occupancy value, no class, no confidence, no time, hand-authored). The object layer has to be ours; there is nothing to inherit.

For this rig the ruling writes itself, and it also answers the scoping doc's open question 1: **objects live beside the locked map, keyed to the map frame, and nothing in the object layer is ever allowed to write back into `m1.json` or the station poses.** The map's job is to be the coordinate system in which object positions are expressed; if the object layer could move the map, every object position would be invalidated by every object update. The one legitimate feedback path is the EDA226 one — cross-map agreement *demoting* an asserted wall's semantics (W6) while leaving its geometry in the navigation grid.

## 3. Re-finding: the search problem, and the result that should scare us

The literature splits into two camps, with an awkward gap in the middle where `locate_object` actually lives:

- **Object-goal navigation** (Habitat ObjectNav, GOAT-Bench, InstanceImageNav) assumes an *unknown* environment and no prior map. Success rates are low — a 2024 method reports **39.0 % SR**, itself a 12.4-point improvement on the prior state of the art. These numbers are not this rig's problem: the rig has a map and a last-known pose, which is a strictly easier task.
- **Instance re-localisation between scans** (3RScan / RIO, ICCV 2019: 1482 RGB-D scans of 478 environments, task = recover the 6-DoF pose of a known object instance in a later scan) is the *right* task definition but is posed offline over two complete scans, not as something a robot does by driving. Its headline number is a caution: **30.58 % re-localisation accuracy** with full RGB-D on both sides. Re-finding a moved object is not an easy problem that only the rover's sensor makes hard.

Between them sits classical **active object search**, whose taxonomy is the useful part: *direct search* (look where the target is believed to be — Garvey 1976) versus *indirect search* (first find a landmark the target is spatially related to, then search near it). Aydemir et al. (T-RO 2013) and Zeng et al.'s SLiM (ICRA 2020) are the reference systems; Zheng et al. (IROS 2021) give the POMDP formulation with an octree belief and a frustum field of view, demonstrated over two 10 m² × 2 m regions with objects at varying heights.

**SLiM's benchmark is the result to build the protocol around.** Searching for a cup with a *known but noisy static* prior on object locations succeeded in **33 %** of trials; the same search with **no** prior succeeded in **83 %**, and with the prior's uncertainty modelled ("known, dynamic") in **83 %**, and with the hybrid strategy in **100 %**. The static-prior run was not merely unhelpful — it was **the worst method tested**, because the robot committed to the place the prior named. In the real-world run (an 8 × 8 m pre-mapped kitchen/living room, Fetch robot) the best method reached **70 % success in 4.86 view poses, 103 s and 8.32 m of driving**, and *every failure was a false-negative detection, not a failed search*.

Two transfers, both of which the recommendation below encodes. First, **a last-known location is a noisy static prior, which is the configuration measured to be actively harmful** — it must carry a covariance that grows with time-since-seen, and the search must be willing to leave it. Second, **the binding failure mode in a pre-mapped room was perception, not navigation.** This rig drives to a commanded pose at 2.5 cm median; the hard half of `locate_object` is the looking, exactly as `docs/next-campaign-scoping.md` already suspects.

**The closest published system to this exact problem is "Where Did I Leave My Glasses?" (RA-L 2026)** — from the POCD authors, so it is the change-detection lineage grown into a search system. Each object carries pose, cloud, bbox, open-vocabulary class, **first-observation and disappearance times**, a geometric-change belief and a stationarity score, plus an **LLM-assigned semantic stationarity label** (static/dynamic) that injects synthetic change for unseen objects, so belief decays faster for things a language model expects to move. The mechanism worth copying is that **search regions are Gaussians whose variance is a function of the stationarity score** — less stationary means a wider search. Reported: 26.35 % higher change-detection F1 than geometric-only on the Khronos dataset, 95 % of map changes detected, and a 29 % efficiency gain over random or patrol search. DynaMem (2024) is the voxel-level cousin and reports **70 % success on non-stationary objects versus 30 % for a static baseline**, with a staleness-driven exploration value map.

The escalation itself — verify in place, re-observe from a few viewpoints, then widen — is the shape all of these take rather than one citable algorithm. The widening step is next-best-view selection, and this wiki already has that machinery in [[active-slam-exploration]] §3: score candidate poses by expected information gain, here over the belief about *one object* rather than over the map.

## 4. Verification: deciding "this is the same object"

Three families, in increasing cost and increasing discriminating power.

**Geometric association** is what the change-detection systems use, and the mechanism is consistent across them: a gated assignment (Hungarian or JCBB) over a cost that mixes centroid distance, orientation and class agreement, with a hard gate so an implausible match is simply refused. POCD's cost is point-to-plane ICP residual plus distance² plus angle plus class mismatch; the reported operating point is 80.2 % precision at 3.0 % false-positive rate on a warehouse dataset ([[dynamic-object-handling]]). The gate is the load-bearing part: an ungated assignment will always produce a match, because assignment problems always have a solution. Fusion++'s gate is worth quoting exactly because it is widely misreported as an IoU: association is **intersection over the *detection's* area > 0.2**, while a separate **3-D bounding-box IoU < 0.5** is what gates *spawning a new object* — two different thresholds doing two different jobs, and the rig needs both (one to match, one to decide something new has appeared).

**Appearance re-ID** is the camera route and is already settled in [[object-fingerprint-memory]] — DINOv2 multi-view max-cosine, precision-favoured threshold, margin as confidence. The honest caveat from the CUTE benchmark (NeurIPS D&B 2023; 18k images, 180 objects under varying lighting and pose) is that the standard perceptual metrics **LPIPS and CLIP scores do not measure object intrinsics well**, which is the same finding that made DINOv2 the pick.

**The failure modes are the reason both are needed.** A second identical chair defeats appearance but not geometry (two records at two places). An object moved 20 cm defeats geometry but not appearance. Occlusion defeats both, and is the case that must never be scored as a negative — see §6. The general rule visible across POCD, Fusion++ and the DovSG update is: **never let one channel alone promote a match.** A strong appearance match at an implausible distance is `uncertain`, not a teleport — [[world-model-architecture]] already states this rule; what this page adds is that on the rover today there *is* no appearance channel, so the geometry gate is carrying the whole load and must be correspondingly conservative.

## 5. What "identified" can mean on a geometry-only sensor

This is the part with no comfortable literature, and the rig-specific content matters more than the citations.

**A single 1.1 m plane gives a 2-D cross-section and nothing else.** From it one can honestly recover: a footprint's position, its extent along the slice, its rough shape class (straight run / corner / curve / thin isolated return), and its persistence across maps. One cannot recover height, volume, colour, material, upright-vs-tipped, or anything that distinguishes two objects with similar cross-sections at that one height. EDA226 states the same thing from the data side: *"the desk is 'a block' because that is what a slice of a desk looks like."* The published 2-D-range recognisers do exist — DROW (wheelchairs and walkers, 464k scans with 24k annotated) and its successors DR-SPAAM and *Deep Person Detection in 2D Range Data* — but note what they are: **single-purpose detectors for one class with a distinctive leg signature, trained on hundreds of thousands of annotated scans.** They are evidence that a 2-D plane carries *some* class information, and equally evidence of the price. That is not a route available here.

So for the first stage, **"identified" should mean a persistent handle, not a name** — which is the honest answer to the scoping doc's open question 4. The object is the same object if it is at the expected place with a compatible footprint and a compatible permanence class. That is a weak test, and it should be reported as one: `found(confidence)`, not `found`.

**What multi-height tilt sweeps add** is the step-change, and it is why the human's thread 4 is the enabling one: several planes turn a cross-section into a coarse vertical profile, which separates a desk from a chair from a box from a wall by *shape at scale* rather than by identity. Zheng et al.'s multi-object-search experiments make the same point from the planning side — their regions are explicitly 2 m tall with objects at varying heights, because a single height does not contain the objects. Two cautions carried from `docs/next-campaign-scoping.md`, both real: a tilted plane breaks the 2-D assumption every current registration makes, and the guard shares the scan plane, so a sweep is a stationary-only operation.

**Where the camera becomes necessary rather than optional** is the moment the question changes from "is something there" to "is it *my* thing". Two same-category instances, a named object, a mug versus a different mug — none of these is reachable from geometry at any number of heights. The camera has been on the rig throughout and has never been used on the rover; June's hand-held hloc relocalised at 96 % and objmem's DINOv2 loop runs, so the pieces exist but the integration is unmeasured. The defensible sequencing (scoping open question 2) is **geometry-only first, because it is the only channel proven on this rover, and add the camera at the verification step** — which is also where SLiM's real-world failures were.

## 6. Change detection: moved, occluded, or gone

The distinction that makes this tractable is **negative evidence**: a cell or object that was *not looked at* is not evidence of absence. EDA226 already implements exactly this and should be recognised as the rig's change-detection substrate rather than a one-off analysis — visibility is computed per map ("a cell is 'looked at' if one of that map's station rays passed through or ended in it"), and the three-way permanent / semi-permanent / unverified split is a direct instance of the [[robust-evidence-mapping-principle]]. The published systems agree on the mechanism, and **Khronos is the one that solves it properly** — worth studying before building this, because it is the design the rig should imitate. Its object node stores `first_observed_ns` / `last_observed_ns` as **vectors — a sequence of presence intervals, not a single pair** — and because positive observations alone cannot separate *gone* from *not looked at*, it maintains a **library of free-space rays** from background points to the observing robot pose, spatially hashed so both endpoints survive loop closure. A timestamp counts as evidence of absence only when **≥ 60 % of rays within a 5 s window** mark the object absent; the disappearance time is then set to the midpoint of the ambiguous window. POCD's cruder version of the same idea: objects *in the frustum but undetected* receive a maximum pseudo-change, so absence counts only when the object should have been visible. The honest limitation to carry: Khronos stores no fragment descriptor, so **it detects that an object went away but cannot re-associate it with the one that appeared elsewhere** — which is precisely the gap an appearance channel fills.

The practical rules, all of which the rig can implement today:

- **Ray-cast the stored footprint from the current station.** If the rays pass *through* where it was, that is observed absence. If they stop short, that is occlusion — and the occluder is itself a useful record. DynaMem does exactly this at voxel level (a voxel in the frustum and not occluded by the current depth is deleted); Khronos's 60 %-of-rays gate is the fraction worth starting from rather than requiring unanimity.
- **Never commit `removed` on one miss.** [[world-model-architecture]] already sets N-consecutive-misses-from-viewpoints-that-should-have-seen-it; the rig's addition is that "should have seen it" is computable from the EDA226 visibility test, not a guess.
- **`τ_move` has a measured floor here**, which is unusually good news: relocalisation with a prior is 0.5 cm / 0.4° median (99 % within 3 cm / 2°), and cross-map registration is ~2 cm rms, so motion above ~5 cm is detectable — far better than the ~⅓ m floor the June camera-based design had to assume. EDA226's cell-exact-versus-one-cell-tolerance experiment (1119 semi-permanent cells collapsing to 549) is the direct measurement of the artefact that sets this floor at 5 cm resolution.
- **Three maps over five days is not a mobility prior.** EDA226 says so itself. Until there are runs across days with deliberate rearrangement, `permanent` means "unmoved in the observations we have", and `locate_object` should treat the permanence class as a *search-width* parameter rather than a truth claim.

## Recommendation for this rig — the `locate_object(handle)` protocol

1. **Store the record beside the locked map, never in it.** One row per object instance in a small store keyed to the office map frame: `handle`, `footprint` (the 2-D points and their fitted extent, not a centroid alone), `position` + covariance, `permanence ∈ {permanent, semi-permanent, unverified}` from the EDA226 cross-map test, `last_seen_ts`, `n_observations`, `state ∈ {present, moved, gone, uncertain}`, and an append-only history. Nothing here may modify `m1.json` or the station poses.
2. **Add the field the classical schemas omit: `last_seen_from`** — the rover pose, tilt angle, range and incidence at which the observation was made, for each of the last few sightings, alongside a *sequence* of presence intervals rather than one `last_seen_ts` (the Khronos form). This is what step 4 drives to, it is what STAR and EmbodiedLGR converged on, and it costs nothing.
3. **Grow the position covariance with time-since-seen, scaled by `permanence`.** A `permanent` object's covariance grows slowly; a `semi-permanent` one's grows fast. This is the SLiM correction — the prior must be dynamic, because a confident stale prior measured *worse than no prior at all* — and it has two published forms to copy: the **persistence filter**'s constant-time Bayesian decay from last-observation time, and "Where Did I Leave My Glasses?"'s rule that **search-region variance is a function of the stationarity score**. The rig's `permanence` class is the input both of them want.
4. **Verify in place first.** Plan to the recorded `last_seen_from` pose (not to the object's coordinates — reproduce the observation, and keep the standoff that worked), stop, relocalise from the odometry prior, capture, clean, and test for a footprint match within the current covariance. Accept only a `strong` unambiguous basin; refuse to conclude anything from a bad relocalisation.
5. **Score the match on three channels, gated.** Centroid distance within the covariance gate; footprint extent and shape compatible; permanence class compatible. Report `found(confidence)` with the margin to the best rival object as the confidence, and never promote a match that fails the distance gate however good the shape agreement.
6. **If not found in place, re-observe from 2–3 viewpoints before believing it.** Choose them for *parallax and incidence* on the stored footprint — different faces, incidence ≤ 70° — inside the drivable band. In a 1.9 × 1.2 m band that is a small, enumerable set; pick it by the observability rule the mapper already uses, not by a spacing heuristic.
7. **Ray-cast before declaring anything absent.** If the stored footprint's cells were passed *through* by this station's rays, that is observed absence → `moved`. If rays stopped short, that is occlusion → `uncertain`, and record the occluder. Absence from a cell nobody looked at is not evidence.
8. **Escalate to a widening search only on an explicit flag, and bound it.** `locate_object(handle, search=True)` searches the drivable band by expected information gain over the object's belief ([[active-slam-exploration]] §3), ordered nearest-first from the last-known position, with a hard budget — 4–6 stations or one battery run, whichever comes first. Default is `search=False`: report `moved` and stop. This is the honest answer to scoping open question 3, and it keeps the first demo inside one charge.
9. **Report a four-way outcome, never a boolean:** `found(confidence, pose)` · `moved(new_pose)` if re-found elsewhere · `absent(searched_region)` if the region was searched and the rays saw through · `uncertain(reason)` for occlusion, bad relocalisation, or budget exhausted. Write every outcome to the object's history with the station pose it was judged from.
10. **Demo it geometry-only, then add the camera at step 5.** A persistent handle re-found across two runs is a complete, honest end-to-end demonstration of the object layer. The camera — hloc for the pose it is already good at, DINOv2 for the identity the LiDAR cannot supply — is the upgrade that turns `handle` into `name`, and its first job should be the verification step, because that is where the reference system's real-world failures were.
11. **Before quoting any number:** ≥ 10 `locate_object` calls over ≥ 2 objects and ≥ 2 sessions, including at least one object deliberately moved and one deliberately occluded, with the outcome and the ground truth recorded by hand each time.
